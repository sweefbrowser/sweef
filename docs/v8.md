# V8 runtime (experimental, opt-in)

Sweef runs page JavaScript on QuickJS, compiled to pure Go and linked into the binary. That stays the default and
the only engine in every shipped build. This page describes the optional second engine: **V8**, loaded at run time
from a separate library. It exists to measure and, later, to decide whether a faster engine is worth shipping. It is
**not** approved as a default: on the pages we measured it is 1.2x to 3.5x faster than QuickJS in page wall time, but
Chromium is still faster than Sweef on most of them, and several features do not work on V8 yet (table below).

The interface the two engines sit behind, and where they differ internally, is in [js-runtime.md](js-runtime.md).

## What it is

* `internal/engine/jsruntime.go`: the `jsRuntime` interface. `qjsRT` is the original QuickJS code moved behind it
  unchanged; `v8RT` (`jsrt_v8*.go`) is the V8 implementation. The ~100 host functions (DOM, fetch, storage, ...) are
  the same Go closures for both.
* `internal/v8shim`: a Go wrapper that calls a C ABI through [purego](https://github.com/ebitengine/purego), so the
  Go side stays `CGO_ENABLED=0`.
* `experimental/v8shim/rust`: a Rust `cdylib` over [rusty_v8](https://github.com/denoland/rusty_v8) (MIT; V8 itself is
  BSD-3-Clause) that exports that C ABI. It is the only place V8 is linked.
* Nothing of this is in the default build. See "Build variants".

## Build it

Library (any platform with a Rust toolchain; the first build downloads rusty_v8's prebuilt static V8, about 100 MB):

```sh
cd experimental/v8shim/rust
cargo build --release --locked
# Linux:   target/release/libsweef_v8shim.so   (about 48 MB)
# macOS:   target/release/libsweef_v8shim.dylib
# Windows: target/release/sweef_v8shim.dll
```

Binary:

```sh
# Linux: the V8 loader is behind a build tag (see below)
CGO_ENABLED=0 go build -tags sweef_v8 -o sweef-v8 ./cmd/sweef
# macOS and Windows: the loader is always compiled in, plain `go build` is enough
```

CI: `.github/workflows/v8-optin.yml` (every PR, one job, Linux x86-64 glibc) builds the library and the `sweef_v8`
binary, checks that the default Linux binary is still static, runs `internal/v8shim` and the `TestV8*` engine tests,
and loads the engine's local fixture pages on V8. `.github/workflows/v8shim.yml` (path-filtered) builds the library on
all six targets (linux, macOS, Windows, x86-64 and arm64), runs the shim tests on each and uploads the libraries as
artifacts.

### Build variants

purego without cgo makes a Linux binary dynamically linked (libc, libdl, libpthread), and Sweef's Linux builds must be
static. So on Linux the loader exists only with `-tags sweef_v8`; the default build has a stub whose `Load` returns
"this build has no V8 support". The tagged variant is glibc-only (no musl) and is about 94 KB larger.
The default release binary is unaffected: it stays static, with the QuickJS engine, under the 41,943,040-byte budget.

## Turn it on

| How | What |
|---|---|
| `--js-engine quickjs\|v8\|auto` | daemon, CLI and GUI flag. Default `quickjs`. |
| `SWEEF_JS_ENGINE=quickjs\|v8\|auto` | environment, overrides the flag and `Options.JSEngine`. |
| `Options.JSEngine` | library users. |

* `v8`: fail loudly. The daemon exits with status 2 when the library cannot be loaded; a library user gets a console
  error per tab. Use this when you want to be sure which engine ran.
* `auto`: V8 if the library loads, otherwise QuickJS with one line on stderr saying why.

Library lookup order: `$SWEEF_V8_LIB` (a file path), then next to the executable, then the working directory.
Other variables:

| Variable | Meaning |
|---|---|
| `SWEEF_V8_LIB` | path of the library |
| `SWEEF_V8_SNAP_DIR` | where the startup snapshot is cached (default `<cache dir>/v8/`) |
| `SWEEF_V8_CODECACHE=on` | V8 code cache (off by default: it helped three of six pages and cost 390 ms on one) |
| `SWEEF_V8_REQUIRE=1` | tests: fail instead of skipping when the library is missing |

The first V8 start builds a startup snapshot of the prelude (about 321 ms, once) and caches it; later starts take
about 33 ms from spawn to first snapshot (QuickJS: 79 ms).

## What works on V8, and what does not yet

| Feature | V8 | Notes |
|---|---|---|
| Classic scripts, ES modules, `import.meta`, dynamic `import()` | works | resolver and loader are the engine's |
| Timers, rAF, microtasks, event loop, settle windows | works | shared code |
| `fetch`, XHR, DOM, storage, events, forms | works | same host functions |
| Script timeout and heap cap | works | the cap ends the isolate; the tab keeps its DOM |
| Unhandled-rejection events | works | (QuickJS never raised them) |
| Agent `evaluate` | works | |
| `Intl`, `WebAssembly` | works, V8's own | the QuickJS WebAssembly host is not used; streaming APIs are added in JS |
| Canvas 2D `getImageData` / `putImageData` fast path | not yet | falls back to the slow path |
| WebGL and WebCodecs value handles (`VideoFrame`, `MediaStreamTrackProcessor`, ...) | not yet | "not supported on the V8 runtime yet" |
| Workers, service workers | not on V8 | they keep running on QuickJS inside a V8 process |
| `SharedArrayBuffer` / `Atomics` with agent clusters and cross-origin isolation | partial | V8's own `SharedArrayBuffer`, no agent cluster, isolation gating not wired |
| WebAssembly host (threads, host imports of the Go side) | not yet | |
| Code cache for ES modules; prefetch of queued `import()` | not yet | |
| Bytecode / precompile of the prelude and scripts | n/a | QuickJS-only mechanism; V8 uses the startup snapshot |

### Known failing test groups on V8

When the engine test suite is run with `SWEEF_JS_ENGINE=v8` (about 45 tests) the failures are in:

* SAB / Atomics (agent-cluster semantics, `DataCloneError` expectations from QuickJS),
* the WebAssembly host (QuickJS-only),
* WebCodecs,
* bytecode and precompile (QuickJS-only mechanism),
* dev-console stack formatting (QuickJS stacks have no header, V8's do),
* and three tests triaged below.

Nothing here changes the default engine; the QuickJS test suite is unchanged and is what CI gates on.

### The three tests that were not triaged at the gate

| Test | Verdict | What happened |
|---|---|---|
| `TestUncaughtReportsThrownValueAndType` | real V8-backend bug, fixed | V8 starts `error.stack` with a header (`Error`), QuickJS does not. For an error with an empty message the prelude printed the header twice (`Uncaught Error: \nError\n    at ...`). `describeThrown` now drops the header when the message is empty; QuickJS output is unchanged. |
| `TestPlatformCoverage` | feature gap, not a regression | `VideoFrame` and `MediaStreamTrackProcessor` are defined by the WebCodecs module, whose value handles are QuickJS-only so far. |
| `TestCompatSiteFeatureDetection` | the same feature gap | the `meet` case probes the same two constructors. |

For the last two the tests now skip (not fail) when the runtime is V8 and the reason is "was not defined by module
webcodecs", with the message pointing here. They go back to running as soon as the handles are ported.

## Measurements (the gate)

Replay proxy (recorded pages, no network noise), median of 7, navigate time in ms, cold / warm (second visit in the
same process), `sweef`'s agent settings:

| page | QuickJS | V8 | speedup | Chromium |
|---|---|---|---|---|
| mdn fetch | 1288 / 1127 | 1024 / 843 | 1.26x / 1.34x | 407 / 228 |
| mdn fetch, equal output (QuickJS with a 2 GiB heap) | 1879 / 1570 | 1036 / 843 | 1.81x / 1.86x | |
| mdn map | 1922 / 1698 | 1367 / 1205 | 1.41x / 1.41x | 442 / 305 |
| pypi | 2216 / 1817 | 634 / 539 | 3.50x / 3.37x | 594 / 330 |
| react.dev | 957 / 676 | 785 / 704 | 1.22x / 0.96x | 499 / 294 |
| learn.microsoft | 2164 / 1403 | 1020 / 930 | 2.12x / 1.51x | 706 / 351 |
| nextjs docs | 765 / 547 | 334 / 284 | 2.29x / 1.93x | 359 / 184 |

Reading them honestly:

* Time spent in the JS engine itself (excluding host functions) is 1.3x to 4.7x lower on V8, not the 5x to 12x a raw
  engine benchmark suggests. Page JS is mostly one-shot compile and first run, plus Go-side host work (forced layout,
  a 27 MB JSON body) that no JavaScript engine removes.
* The first MDN row compares against QuickJS's output at the old 256 MiB heap cap, which truncated the page (the
  cap is being raised in a separate change, `fix(engine): raise the per-tab JS heap cap`); the "equal output" row is
  the fair one.
* Chromium is faster than Sweef-on-V8 on five of the six pages (pypi is on par). Sweef's case is token cost, memory
  and start-up, not raw page speed.
* Start-up: spawn to first snapshot through MCP, QuickJS 79 ms, V8 with a cached snapshot 33 ms, V8 on the first run
  without a snapshot 321 ms. VM build 7.8 ms vs 27.5 ms.

## Shipping the V8 library: plan (not done, nothing is published)

This section is a plan. Today the library is a CI artifact only.

**Targets** (the six `v8shim.yml` matrix entries): linux-x64 and linux-arm64 (glibc only, no musl: rusty_v8 has no musl
build and the loader needs the dynamic libc anyway), macos-x64, macos-arm64, windows-x64, windows-arm64. Library sizes
are in the CI step summary (Linux x64 about 48 MB).

**Artifacts.** Per target: the library plus, for Linux only, the `sweef_v8` build of the binary (named `sweef-v8`).
On macOS and Windows the standard binary already contains the loader, so only the library is added. Publish them as
extra assets of the release next to the normal archives, with SHA-256 sums in the existing checksum file.

**Signing.**

* macOS: the library must be signed with the same Developer ID as the binary, with the hardened runtime. V8 needs
  JIT, so the main executable (the process that maps the JIT pages) needs the entitlement
  `com.apple.security.cs.allow-jit`; the library is loaded with `dlopen`, so the executable must also allow loading a
  library signed by the same team (library validation is satisfied by the same Team ID, otherwise add
  `com.apple.security.cs.disable-library-validation`, which we want to avoid). Notarize the archive (the library inside
  it) and staple the ticket to the app or pkg where there is one.
* Windows: Authenticode-sign `sweef_v8shim.dll` with the certificate that signs `sweef.exe`; SmartScreen and AV
  reputation are per signed file.
* Linux: no signing; the checksum and the release signature cover it. glibc 2.31 or newer is assumed (the CI runner's
  is newer; the exact floor must be measured on the artifact with `objdump -T` before it is documented).

**How the SDK installers would fetch it.** The Node and Python SDK installers already download the `sweef` binary for
the platform. A new opt-in step (`SWEEF_INSTALL_V8=1` or `sweef-install --v8`) would download `sweef-v8` (Linux) or the
library (macOS, Windows) for the same version and platform, verify the SHA-256 from the release checksums, and place
the library next to the executable, which is the second entry of the lookup order, so no environment variable is
needed. `--js-engine auto` then picks it up and falls back to QuickJS when it is absent. The default install never
downloads it.

**Before any of that:** a decision on the V8 default (not approved), the feature gaps above (workers, WebCodecs and
canvas handles, SAB isolation, module code cache), a measured glibc floor, a size budget for the extra download, and
a release job that runs the V8 smoke tests on the signed artifacts.
